# Flowup CLI 试用记录

2026-09-30，在 Windows 上使用 Go 1.26.3，从源码构建并实际运行 CLI。完成了 47 项命令检查，另外启动并中断了两次运行进程，验证新进程能否接手。

本地 JSON、审批、状态查询、进程中断和恢复都使用真实 CLI 与 SQLite。HTTP 和模型接口由本机模拟服务提供，使用虚构的凭据。这轮检查未使用真实模型、GitHub 或 Slack 凭据，因此不把这些检查算作真实平台联调。

## 实际试了什么

| 操作 | 观察到的结果 |
| --- | --- |
| 本地分流 | `high` 输出 `notify`，`low` 输出 `ignore`；没有发送消息 |
| 查询状态和事件 | `status` 显示步骤状态；`trace` 输出逐行 JSON，包含运行和步骤的开始、结束 |
| 缺少输入、输入类型错误 | 返回 `invalid_inputs`，退出码为 2 |
| 条件分支 | 条件为假时跳过步骤，后续可以根据 `steps.ID.status` 判断 |
| JSON Schema 校验 | 类型不匹配时运行失败；`json.select` 的数组索引会被拒绝 |
| 审批 | `run` 返回 `waiting_approval` 并退出；另一个 CLI 进程批准后继续完成 |
| 拒绝和重复审批 | 拒绝结束运行；已批准的审批再次批准会报错 |
| 等待审批时恢复 | `resume` 报错，不能绕过审批 |
| HTTP 网络限制 | 本机地址默认被拒绝；显式允许私网后可访问；主机白名单继续生效 |
| HTTP 重试 | 模拟 GET 前两次返回 503，第三次成功；POST 返回 503 时只收到一次请求 |
| AI 输入和输出 | 请求只包含配置的提示词和投影输入，没有工具；结构化输出经过本地 Schema 校验 |
| AI 模型切换 | 设置两次尝试和两个模型，第一次返回不符合 Schema 的内容，第二次成功 |
| AI 限流 | 显式设置两次尝试后，可从模拟 429 恢复；默认配置只请求一次，随后失败 |
| 读取 → AI → 审批 → 写入 | 审批前没有发出写请求；批准后发送一次，前面的读取和模型调用没有重复 |
| 相同幂等键 | 相同动作、相同输入和同一数据库内，两次运行使用相同键，只发送一次 POST |
| 读操作期间结束进程 | `resume` 重做未完成的 GET，前面已经完成的步骤不重做，最后成功 |
| 写操作期间结束进程 | 模拟服务已收到 POST，但 CLI 尚未记录完成时被结束；恢复返回 `effect_indeterminate`，没有再次发送 POST |

新加入的本地分流输入、审批示例和 AI 分类示例均通过 `validate`。前两类已离线运行，AI 分类示例使用模拟模型运行。

`go test ./...` 和 `go vet ./...` 通过。源码构建和安装到独立临时目录也通过。仓库中的 GitHub、Slack 连接器测试及 issue 分流验收测试通过，但使用的仍是模拟服务。

## 使用时遇到的问题

### 审批时看不到待确认内容

`run` 输出审批 ID 和批准、拒绝命令，没有输出 `message` 或 `preview`。审批说明能在 `trace` 的 `approval.requested` 事件中看到，预览内容没有对应的查看命令。

原因在 [printApprovalCommands](../cmd/flowup/commands.go)：这里只打印了 ID 和命令。新本地示例把要确认的文字也放进 `message`，README 说明了查看方法。

### 不同错误在终端里看起来一样

缺少模型配置、JSON Schema 不匹配、HTTP 调用失败，都可能显示：

```text
action_permanent: execute action
```

[引擎](../internal/engine/engine.go)把具体错误存进步骤记录，但运行级错误统一写成 `execute action`；[错误类型](../internal/engine/errors.go)的字符串没有带上底层原因，`status` 也不展示步骤的错误说明。用户仅靠常用命令很难判断要修哪里。

### 失败任务的 resume 不会重试，而且返回 0

让 `json.validate` 校验失败后再执行 `resume`，输出仍是 `status: failed`，退出码却是 0。它返回了终态记录，没有执行步骤。

这和从中断的 `running` 状态恢复是两种行为。[使用指南](usage.md)已分别说明，脚本不能只看 `resume` 的退出码。

### 脱敏不会清理所有响应内容

测试给本地 HTTP 服务发送了虚构的凭据 `qa-secret-for-echo`，让服务在普通 `echo` 字段中原样返回。数据库里动作输入中的凭据变成了 `[REDACTED]`，但步骤输出和最终输出仍包含原值。

输入中的秘密引用由 [ResolveSecrets](../internal/policy/secrets.go)遮住；步骤输出在保存前没有按已解析的秘密值清理。因此原 README “步骤记录和事件只持久化脱敏值”的承诺过宽，已改成具体说明。

### AI 的 token 数被当成秘密遮住了

模拟服务返回输入 12、输出 5 个 token，`ai.attempt` 事件中的 `input_tokens` 和 `output_tokens` 都变成了 `[REDACTED]`。

原因是 [事件脱敏规则](../internal/policy/secrets.go)按字段名匹配 `token`，误伤了用量计数。当前不能通过这些事件准确统计 token 用量。

### 重试规则没有原说明写得那么统一

实测 HTTP GET 自动重试，AI 默认一次，需要配置 `max_attempts` 才增加尝试。源码检查还发现，GitHub、Slack 客户端返回的临时错误没有接入引擎的可重试标记。

使用指南已按动作分别说明。GitHub、Slack 的这一项来自代码检查，未对真实平台制造限流来验证。

### CLI 帮助和配置还有小绊脚石

`flowup --help` 会先报 `unknown command "--help"`，再打印用法，退出码为 2。当前没有版本查询或列出全部运行的命令。

配置模板原来让用户复制成 `model.env`，但程序只读取进程环境变量。模板注释和使用指南现已明确说明不会自动加载文件。

## 本次文档和示例调整
